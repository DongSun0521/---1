# Combat V2：阵型塔防原型

## MVP 验证目标

Combat V2 MVP 用于验证“多路敌人向村庄推进，角色组成防线并自动作战”的核心循环
是否清晰、可操作且值得继续扩展。验证过程应优先关注战场信息可读性、阵型决策和
基础胜负反馈，不接入正式养成经济。

## 当前实现：V2-1

V2-0 建立了可独立运行、可整体删除的原型环境。V2-1 在该环境内完成三路敌人进攻
同一个村庄入口的基础循环：

- 右侧上、中、下三个刷怪口和三条软路线；
- 三路在左侧汇入同一个村庄入口；
- 确定顺序生成的占位敌人和匀速路径点移动；
- 单次漏怪结算、10点村庄耐久和耐久归零保护；
- `READY`、`RUNNING`、`VICTORY`、`DEFEAT` 四种互斥状态；
- 开始、重新开始、方案选择和实时统计界面。

V2-1 没有角色、攻击、生命、死亡、阻挡、组阵、集火、技能、正式波次或奖励。

目录约定：

- `scenes/`：原型专用场景；
- `scripts/`：原型专用运行脚本；
- `data/`：后续原型数值和数据资源；
- `tests/`：只验证原型入口与隔离边界的自动化检查。

## 当前入口

入口场景：

```text
res://prototype/formation_defense/scenes/formation_defense_prototype.tscn
```

在 Godot 编辑器中打开该场景后选择“运行当前场景”（F6），即可单独启动。也可在
项目根目录运行：

```powershell
tools\godot.bat --path . `
  res://prototype/formation_defense/scenes/formation_defense_prototype.tscn
```

## 操作与测试方案

开始前可选择：

- **生存演示**：上、中、下路各2只，共6只；全部漏入后村庄剩余4点耐久并进入
  `VICTORY`；
- **失守演示**：上、中、下路各4只，共12只；第10只漏入后耐久归零，立即进入
  `DEFEAT` 并清理剩余敌人。

生成顺序和间隔固定。这些方案仅用于 V2-1 基础循环验证，不是正式波次设计。
战斗中“开始”和方案选择会被锁定；“重新开始”会恢复耐久、计数、状态、生成进度
和提示，并清理全部旧敌人。

## V2-1 代码职责

- `data/formation_defense_config.gd`：耐久、速度、漏怪伤害、归一化路线点和测试
  生成计划；
- `scripts/formation_defense_prototype.gd`：生成、状态、耐久、胜负和重开；
- `scripts/formation_defense_enemy.gd`：单个敌人的路径进度、位置与一次性抵达报告；
- `scripts/formation_defense_route_view.gd`：软路线轨迹和点状方向提示；
- `tests/smoke_v2_1_basic_loop.gd`：确定性胜败、重开、幂等和隔离验收。

## 与正式系统的隔离原则

- 不替换默认主场景，不注册 Autoload，不增加正式入口；
- 原型运行时不读取或写入 `GameState`；
- 不接入 `CharacterRoster`、`SaveSystem` 或正式存档；
- 不读取正式角色、装备、建筑、战斗场景和正式数值配置；
- 原型运行资源的依赖必须保持在本目录内或使用 Godot 内建资源；
- 后续原型数值统一放入本目录的 `data/`；
- 删除整个 `formation_defense/` 目录后，正式项目应保持原有行为。

## 后续边界

V2-2 及之后才会考虑角色部署、自动选敌和攻击等内容。当前没有提前实现四名角色、
投射物、伤害、阻挡、敌人生命/死亡、怪物组阵、阵型连线、集火、技能/大招、
村庄支援、正式五波、Boss、奖励、装备、育成、探索或存档接入。
